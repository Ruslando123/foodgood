# FoodGood: поэтапный план архитектуры и развития

Цель: вырастить текущий MVP в надежную платформу для заказа surprise-bag еды, похожую по качеству продукта и устойчивости на delivery-сервисы уровня Яндекс Еды, но без преждевременного усложнения.

## Принципы

- Сначала монолит с чистыми границами, потом выделение сервисов только там, где появилась реальная нагрузка.
- Деньги, заказы, остатки и выдача должны быть консистентными даже при двойных кликах, плохой сети и параллельных запросах.
- Все критичные операции должны иметь audit trail: кто, когда и почему создал, оплатил, отменил, выдал или вернул заказ.
- Любая новая функция должна иметь метрики: конверсия, ошибки, скорость, влияние на выручку.
- Мобильный UX важнее desktop: основной сценарий будет в Telegram WebView и мобильном браузере.

## Этап 1. Укрепить MVP

Срок: 1-2 недели.

Цель: сделать текущую версию стабильной для закрытого теста.

### Архитектура

- Оставить Next.js-монолит, но разделить код по доменам: `auth`, `catalog`, `orders`, `payments`, `merchant`, `notifications`.
- Вынести бизнес-правила из route handlers в сервисные функции, как уже сделано в `src/lib/orders.ts`.
- Добавить единый формат ошибок API: `code`, `message`, `details`.
- Добавить middleware для auth, role checks и rate limiting.
- Добавить валидацию входных данных через Zod или аналог.

### Данные

- Перейти с SQLite на PostgreSQL.
- Добавить Prisma migrations вместо `db push`.
- Добавить индексы под реальные запросы: активные пакеты по городу, заказы пользователя, заказы заведения, выдача по `pickupCode`.
- Добавить таблицы `AuditLog`, `Notification`, `PaymentEvent`.

### Надежность

- Добавить idempotency key для создания заказа и платежных операций.
- Добавить retry-safe capture/refund.
- Добавить job-воркер для истечения заказов и возвратов.
- Добавить structured logs с `requestId`, `userId`, `orderId`.

### Страницы

- Главная: фильтры по категории, цене, времени выдачи, расстоянию.
- Карточка пакета: условия выдачи, состав может отличаться, политика возврата.
- Заказы: таймер до окна выдачи, понятный статус возврата, адрес и маршрут.
- Бизнес-кабинет: редактирование и снятие пакета с продажи, список заказов по пакету.
- Логин: нормальная отправка SMS, повтор кода, лимиты попыток.

## Этап 2. Production-ready пилот

Срок: 2-4 недели.

Цель: запустить пилот на реальных заведениях и платежах.

### Инфраструктура

- Deploy: Vercel/Render/Fly.io для приложения, managed PostgreSQL для базы.
- Отдельные окружения: `dev`, `staging`, `production`.
- Secrets management: платежи, SMS, Telegram, JWT secret.
- CI pipeline: lint, typecheck, test, build, migrations check.
- Backups PostgreSQL и rollback-процедура.

### Платежи

- Реальный provider: CloudPayments, Freedom Pay, Kaspi Pay или другой доступный в Казахстане.
- Webhooks платежного провайдера.
- Статусы платежей отделить от статусов заказов: `PaymentIntent`, `PaymentTransaction`, `Refund`.
- Реконсиляция: регулярная сверка локальных платежей с провайдером.

### Нагрузка

- Добавить Redis для rate limit, короткого cache и lock/idempotency.
- Кэшировать список активных пакетов по городу/району на 15-60 секунд.
- Добавить pagination/cursor для списков.
- Ограничить дорогие запросы и payload API.
- Настроить CDN для статических изображений заведений.

### Операции

- Админка для модерации заведений.
- Ручная отмена заказа и возврат.
- Просмотр audit log.
- Управление комиссиями и payout-статусами.

## Этап 3. Хороший продукт для покупателя

Срок: 1-2 месяца.

Цель: поднять конверсию и повторные покупки.

### Главная страница

- Поиск по названию заведения, блюду, району.
- Фильтры: сейчас можно забрать, рядом, до 1500 ₸, скидка 60%+, категория.
- Сортировка: рядом, скоро закончится, лучшая скидка, популярное.
- Избранные заведения.
- Блоки: "Рядом с вами", "Скоро забрать", "Лучшие скидки", "Супермаркеты", "Пекарни".

### Карта

- Кластеры заведений.
- Bottom sheet с карточками.
- Построение маршрута через 2ГИС/Яндекс/Google Maps.
- Состояния: нет геолокации, нет пакетов рядом, город не поддерживается.

### Карточка пакета

- Фото заведения и примеры содержимого.

- Правила выдачи: где вход, что сказать на кассе, нужен ли QR.

### Заказы

- Live-статусы: оплачен, скоро выдача, можно забирать, выдан, возврат.
- QR + короткий код + offline fallback.
- Кнопка "построить маршрут".
- Повторить заказ.
- Оценка после выдачи.

### Профиль

- Имя, телефон, Telegram.
- Избранное.
- История экономии и "спасенной еды".
- Поддержка и обращения.
- Управление уведомлениями.

## Этап 5. Платформа под высокую нагрузку

Срок: после подтверждения спроса.

Цель: выдерживать всплески трафика, распродажи и рост городов.

### Целевая архитектура

```text
Client / Telegram WebApp
        |
Next.js Web + BFF API
        |
Domain modules inside monolith
        |
PostgreSQL + Redis + Object Storage
        |
Background Workers + Payment/SMS/Telegram providers
        |
Admin / Analytics / Support tools
```

### Когда выделять сервисы

- Payments service: когда появятся реальные webhooks, реконсиляция и несколько провайдеров.
- Notifications service: когда SMS/Telegram/push/email станут массовыми.
- Search service: когда фильтров и городов станет слишком много для простого PostgreSQL.
- Analytics pipeline: когда нужны отчеты без нагрузки на production DB.

### Масштабирование

- Read replicas для тяжелых чтений.
- Очереди: BullMQ/Redis, Cloud Tasks или managed queue.
- Geo queries: PostGIS вместо ручного haversine при росте каталога.
- Search: PostgreSQL full-text сначала, Meilisearch/Elastic позже.
- Observability: Sentry, OpenTelemetry, Prometheus/Grafana или managed APM.
- Load tests: k6 сценарии на каталог, покупку, оплату, выдачу.

### Критичные SLA

- Каталог пакетов: p95 до 300 мс.
- Создание заказа: p95 до 800 мс без учета платежного провайдера.
- Выдача по QR: p95 до 500 мс.
- Ошибки API: ниже 1%.
- Двойная продажа остатка: 0 случаев.
- Потерянные платежи/refunds: 0 случаев.

## Этап 6. Функции уровня большого delivery-сервиса

- Персональные рекомендации.
- Промокоды, бонусы, referral.
- Dynamic pricing для пакетов, которые скоро истекут.
- Подписка или абонемент на скидки.

4. Спринт 4: фоновые jobs, уведомления, возвраты по расписанию.

8. Спринт 8: нагрузочное тестирование, мониторинг, production hardening.

## Первое практическое решение

Не начинать с микросервисов. Правильный следующий шаг — production-ready modular monolith:

- один Next.js app;
- PostgreSQL как источник истины;
- Redis для rate limits, locks, queues;
- background worker рядом с приложением;
- строгие доменные модули;
- audit/payment/notification события;
- observability с первого пилота.

Такой путь быстрее для разработки, дешевле в эксплуатации и легче масштабируется до первых реальных нагрузок. Сервисы стоит выделять только после того, как метрики покажут конкретное узкое место.
